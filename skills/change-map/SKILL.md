# Change Map

Generate visual diagrams that tell the **story** of code changes. The output is GitHub-compatible markdown with mermaid diagrams — works both in the terminal and copy-pasted into PR descriptions.

The goal is minimum mental load for reviewers: they should glance at the diagrams and immediately know WHERE to look and WHY, not just WHAT changed.

## Execution

Spawn a subagent to do all the heavy lifting. The main conversation stays clean — you just relay the final markdown output.

```
Agent(
  description: "Change Map: <branch-or-context>",
  subagent_type: "general-purpose",
  prompt: <see below>
)
```

Use a short descriptive label with context, e.g.:
- `"Change Map: feature/sso-v2-migration"`
- `"Change Map: uncommitted changes"`
- `"Change Map: last 3 commits"`

### Subagent prompt template

Adapt based on context (branch name, custom diff range, etc.):

```
Generate a visual change map for code changes. Output ONLY the final markdown block — no commentary, no explanations.

Follow these phases strictly in order. Do NOT skip ahead to diagram generation before completing the research phases.

## Phase 1: Git Context (use Bash tool)

Determine the base branch and gather all diff data in parallel where possible.

**1a. Find base branch and store it:**
```bash
BASE_BRANCH=$(git fetch --quiet 2>/dev/null; for b in origin/dev origin/develop origin/main origin/master; do git rev-parse --verify "$b" >/dev/null 2>&1 && echo "$b" && break; done)
echo "$BASE_BRANCH"
```

**1b. Gather all git context in ONE bash call:**
```bash
echo "=== REPO ===" && git remote get-url origin && git branch --show-current && \
echo "=== COMMITS ===" && git log $BASE_BRANCH..HEAD --format="%h %s" && \
echo "=== BRANCH DIFF STAT ===" && git diff $BASE_BRANCH...HEAD --stat && \
echo "=== UNCOMMITTED STAT ===" && git diff --stat && git diff --cached --stat && \
echo "=== PR ===" && gh pr view --json title,url 2>/dev/null || true
```

**1c. Get the full diff (second bash call):**
```bash
git diff $BASE_BRANCH...HEAD -- . ':!*.generated.*' ':!*.lock' ':!**/types.ts' ':!**/__generated__/**' && \
echo "=== UNCOMMITTED ===" && \
git diff -- . ':!*.generated.*' ':!*.lock' ':!**/types.ts' ':!**/__generated__/**'
```

**1d. If diff > 500 lines:** Stop reading the full diff. Use the `--stat` output to identify changed files — you'll read them in Phase 2 anyway.

## Phase 2: Generate File Dependencies Diagram (use Bash tool — ONE call)

The File Dependencies diagram is generated by a bundled script. Run it and capture the output:

```bash
node "${CLAUDE_SKILL_DIR}/scripts/file-deps.mjs"
```

The script handles everything: git diff parsing, import resolution, symbol extraction, base-branch comparison, mermaid generation with classDef, subgraph styling, linkStyle, click URLs. It runs in <1 second.

Save its output — this becomes the "### File Dependencies" section of the final markdown.

## Phase 2b: Generate Symbol Map (use Bash tool — ONE call)

The Symbol Map provides a JSON lookup of every function/const/type definition in changed files, with pre-built clickable URLs. Run it and capture the output:

```bash
node "${CLAUDE_SKILL_DIR}/scripts/symbol-map.mjs"
```

This outputs a JSON object keyed by symbol name. Exported symbols use their name directly (e.g. `"handlePostAuthConsent"`). Non-exported symbols are prefixed with their file path (e.g. `"providers/auth-provider:login"`). Each entry has `file`, `line`, `kind`, and `url`.

Save this output — you will use it in Phase 4 to build accurate `click` directives for the Logical Flow diagram. **Do NOT guess line numbers or construct URLs manually — always look up the symbol in this map.**

## Phase 3: Story Analysis (no tools — think)

Read the script output from Phase 2 and the diff from Phase 1. Before generating the Logical Flow diagram, answer:
- What is the main behavior change or feature?
- What are the key decision points / branching paths?
- What is the entry point a reviewer should start from?
- Which files are central (most connections in the script output)?

## Phase 4: Generate Output

Output a single markdown block with this structure:

### Change Map heading

### Logical Flow — mermaid flowchart TD
Shows HOW the code flows through the changes with decision paths.

**Init directive:** Add `%%{init: {'flowchart': {'wrappingWidth': 9999}}}%%` as first line to prevent text wrapping.

**Node shapes:**
- Use rounded rectangles `("label")` for action nodes — NOT sharp rectangles `["label"]`
- Use decision diamonds `{"condition?"}` for branching logic

**Content:**
- Label nodes as `file: functionName()` so reviewers know where to look
- Show 3-8 key paths — tell the story, don't overwhelm
- Use descriptive edge labels (`|success|`, `|401 error|`, `|already registered|`)
- Group with `subgraph` using explicit IDs when it clarifies layers

**Styling — match file dependencies diagram:**
- Color new nodes: `style X fill:#4ade80,color:#000,text-align:left`; modified: `style X fill:#60a5fa,color:#000,text-align:left`
- Always include `color:#000` and `text-align:left` in every style directive
- Subgraph panes: `style ID rx:10,ry:10,fill:#1e293b,stroke:#334155,color:#94a3b8`

**Arrow styling:**
- Use `linkStyle default stroke:#475569,stroke-width:1.5px` as baseline
- Color happy-path arrows green: `linkStyle N stroke:#4ade80,stroke-width:2px`
- Color error-path arrows red: `linkStyle N stroke:#f87171,stroke-width:2px`
- Links are numbered by order of appearance (0-indexed) — count carefully

**Clickable links:** Use the Symbol Map from Phase 2b to add `click` directives. Each entry has a `label` field (e.g. `"providers/auth-provider: handlePostAuthConsent() :102"`) and a `url` field. Use the `label` for the node text and `url` for the click target. Always add `_blank` to open in a new tab. Example: if the symbol map has `"handlePostAuthConsent": {"url": "https://...R102", "label": "providers/auth-provider: handlePostAuthConsent() :102"}`, use:
- Node: `E("<u>providers/auth-provider: handlePostAuthConsent() :102</u>")`
- Click: `click E "https://...R102" _blank`
**NEVER guess line numbers or construct URLs manually** — always look up from the symbol map. If a symbol isn't found, omit the click directive for that node.

**Underlines:** Wrap node labels in `<u>` tags for nodes that have click links, to signal clickability.

- SKIP this diagram if changes are purely structural (renames, moves) with no branching

### File Dependencies — generated by script
The `file-deps.mjs` script output from Phase 2 IS this section. Include it directly in the final output as `## File Dependencies` followed by the mermaid code block the script produced. Do not regenerate or modify it — the script handles all styling, symbols, click URLs, and subgraph grouping.

## Scaling rules
- Small (1-3 files): Skip flow diagram unless meaningful branching exists
- Medium (4-10 files): Full treatment
- Large (10+ files): Multiple flow diagrams by feature area, keep each under ~30 mermaid nodes
- Pure refactor: Skip flow, show before→after in dependency diagram
```

### What you do with the result

The subagent returns the complete markdown block. Output it directly to the user — they can:
1. Review it in the terminal
2. Copy-paste into a PR description (mermaid + links render natively on GitHub)

If the user wants adjustments (more detail, different grouping, focus on a specific area), you can either edit the output directly or re-run the subagent with refined instructions.
